## 1. 개요

### 1.1 한 줄 정의
사용자가 정한 목표에 맞춰 AI 에이전트 팀이 웹소설을 자율적으로 기획하고 연재합니다. 필요한 결정은 Discord나 Telegram으로 사용자에게 묻고 답을 반영하며, 세계관 온톨로지(Graph DB)로 설정 일관성과 떡밥(복선) 설치·회수를 관리합니다. 완성된 화는 씬 단위 프롬프트, 이미지, 영상으로 확장합니다.

### 1.2 배경과 문제
1. **장편 연재는 일관성을 유지하기 어렵습니다.** 웹소설은 수백 화 단위로 연재되고, 공개된 회차는 사실상 고칠 수 없습니다. 초반 복선을 잊고, 인물마다 아는 정보가 다르고, 회귀·루프물에서는 같은 사건이 여러 시간선에 존재합니다. 장편을 "제대로 끝내는 것"이 가장 어렵다는 작가 회고가 있습니다 [2차]. 설정 붕괴나 떡밥 미회수를 정량화한 조사는 찾지 못했습니다 [미확인].
2. **연재 주기가 빠듯합니다.** 유료 연재 1화는 공백 포함 약 5,000~5,500자가 관행입니다 [2차]. 일일 연재 관행은 출처를 확보하지 못했지만 [미확인], 하루 1화 이상을 버틸 수 있는 생산 능력이 필요하다고 판단합니다(가정).
3. **기존 AI 글쓰기 도구는 대화형 보조에 머뭅니다.** 사람이 매번 프롬프트를 넣어야 하고, 작품 단위의 장기 기억(세계관, 떡밥, 공개 이력)을 구조화해 보관하지 않습니다. 가정: 경쟁 제품은 조사하지 않았습니다. 이 주장을 차별점으로 쓰기 전에 비교 조사가 필요합니다(D-23).
4. **자율 에이전트는 사람의 판단을 받을 통로가 필요합니다.** 사용자가 대시보드 앞에 계속 앉아 있지 않으므로, 이미 쓰는 메신저로 짧게 묻고 답을 받아 반영해야 합니다.
5. **AI 생성물에는 정책과 법적 제약이 있습니다.** 일부 국내 플랫폼과 공모전은 AI 작품을 제한하고 [2차], 사람의 창작적 기여 없이는 저작권 보호를 장담할 수 없습니다 [2차]. 사람이 언제 무엇을 결정하고 고쳤는지 기록이 남아야 합니다.

### 1.3 제품 비전
- **작품을 "운영"하는 스튜디오**: 사용자는 쇼러너(총괄 PD) 역할을 합니다. 방향, 승인, 예산을 정하고, 에이전트 팀이 기획 → 집필 → 검수 → 연재를 반복합니다.
- **세계관이 살아 있는 데이터**: 인물, 장소, 사건, 규칙, 떡밥, 인물별 지식 상태를 시점과 버전이 있는 그래프로 관리합니다. 세계관 사실·관계·떡밥 연결의 단일 원천은 Graph DB이고, 집필·검수·미디어 생성이 모두 이 그래프를 조회합니다.
- **사람 개입은 적게, 기록은 확실하게**: 되돌릴 수 없거나 영향이 큰 결정만 묻습니다. 답변은 무엇이 어디에 반영됐는지까지 기록하고 사용자에게 알립니다. 모든 결정, 승인, 수정은 감사 로그에 남깁니다.
- **텍스트에서 미디어로**: 완성된 화를 씬 단위로 나눠 이미지·영상 프롬프트를 추출하고, 씬 이미지와 씬 영상을 만듭니다. 트레일러는 씬 영상 위의 편집 산출물입니다. 캐릭터 외형도 같은 온톨로지에서 가져와 시각 일관성을 유지합니다.

## 2. 목표와 비목표

### 2.1 목표
아래 수치는 초기 목표입니다. 가정: 기준 측정 전이므로 MVP 내부 검증(dogfooding) 후 다시 정합니다. 지표 정의는 9절 KPI 표 하나를 기준으로 하고, 이 표는 그 KPI를 참조합니다.

| ID | 목표 | 측정 기준 (9절 KPI) | MVP 목표치 | 릴리스 |
|---|---|---|---|---|
| G-0 | 읽을 만한 소설을 만든다 | 블라인드 품질 평가 점수, 무수정 승인 비율 | 평가 중앙값 3.5/5 이상 (가정), 무수정 승인 비율은 측정만 | MVP |
| G-1 | 사용자 목표만으로 연재가 굴러간다 | 자율 연속 승인 화 수 | 장르 2개 × 각 30화 이상 (가정) | MVP |
| G-2 | 연재 속도를 유지한다 | 화당 생성 시간 | 중앙값 60분 이하 (가정) | MVP |
| G-3 | 설정 일관성을 지킨다 | 연속성 오류율(측정 프로토콜 포함), 연속성 사전 검출률 | 측정 후 설정 (참고 가정: 0.3건/화 이하) | MVP |
| G-4 | 떡밥을 회수한다 | 기한 초과 처리율, 떡밥 회수율, 떡밥 폐기율 | 기한 초과 처리율 90% 이상, 회수율·폐기율은 따로 보고 | MVP |
| G-5 | 사람 개입을 줄이되 답변은 확실히 반영한다 | 화당 차단형 질문 수, 답변 반영 성공률 | 화당 차단형 1건 이하 (가정), 반영 성공률 100% | MVP |
| G-6 | 비용을 예측하고 통제한다 | 예약 상한 기준 한도 초과 건수, 실집행 초과액 | 예약 상한 기준 초과 0건, 실집행 초과는 진행 중이던 호출 1건 이내 | MVP |
| G-7 | 사람 기여를 증명할 수 있다 | 회차별 사람 결정·수정 기록 내보내기 가능 비율 | 100% | v1 (기록 데이터는 MVP부터 수집) |
| G-8 | 씬 미디어를 저비용으로 만든다 | 채택 삽화 1장당 비용 | 0.5 USD 이하 (가정) | v1 |
| G-9 | 화를 씬 단위 영상까지 만든다 | 씬 영상 완료율 | 대상 화의 대상 씬 100% (필터 차단은 사유와 함께 별도 집계) | v2 |

### 2.2 비목표
- **국내 주요 플랫폼 투고 대행**: 플랫폼 업로드 자동화와 투고 대행은 하지 않습니다. 정책 충돌 위험이 크기 때문입니다(10절). 앱 안의 "공개 처리"는 사용자가 외부에 공개했다는 표시이며 업로드가 아닙니다.
- **AI 탐지 회피**: AI 생성 사실을 숨기거나 탐지를 우회하는 기능은 만들지 않습니다.
- **독자용 연재 플랫폼**: 독자 커뮤니티, 결제, 랭킹은 범위 밖입니다.
- **실존 인물 기반 창작과 실사 얼굴 합성**: 막습니다. 실존 인물 사칭·명예훼손 텍스트와 실존 인물 얼굴 합성 차단은 사용자가 끌 수 없습니다(NFR-SAFE-02).
- **웹툰 자동 제작(MVP~v2)**: 말풍선, 컷 분할, 수십 컷 단위 일관성이 필요해 v2 이후 후보로 둡니다.
- **자체 모델 학습과 GPU 운영(MVP~v1)**: LoRA, 자체 호스팅 영상 모델은 후속 옵션으로 둡니다.
- **카카오톡 채널(MVP)**: 봇이 먼저 보내려면 사업자 인증과 유료 Event API가 필요합니다 [1차].
- **Paperclip 코드베이스 직접 포크**: 패턴과 범용 인프라를 참고할 뿐, 그 도메인(AI 회사 운영)을 그대로 가져오지 않습니다(14.2절).

## 3. 대상 사용자와 페르소나

가정: 1차 타깃은 개인 사용자의 로컬 또는 자체 호스팅 환경입니다(13절 D-1, D-2).

### P1. 실험형 창작자 "민준" (1차 타깃, MVP)
- 30대 개발자. 웹소설 독자이며 AI 도구에 익숙합니다.
- 목표: 머릿속 설정으로 장편을 끝까지 완성해 보고, 자체 채널이나 해외 플랫폼에 AI 생성 고지를 붙여 올립니다.
- 불편: 직접 쓰기에는 시간이 없고, 대화형 AI로는 50화쯤에서 설정이 무너집니다.
- 기대: 퇴근길에 Telegram으로 질문 2~3개에 답하면 다음 날 아침 새 화가 준비되어 있고, 내 답이 어디에 반영됐는지 알림으로 확인합니다.

### P2. 현업 작가 "서연" (작가 보조 용도, v1 이후 후보)
요구 1(에이전트가 자율로 만든다)과 방향이 다른 사용 형태라 MVP 대상이 아닙니다. `co_writing` 모드와 함께 v1 이후 후보로 둡니다(잠정: D-20).
- 로판 유료 연재 작가. 주 5회 이상 연재합니다(가정).
- 목표: 직접 집필은 유지하면서 설정 관리, 떡밥 추적, 다음 화 기획 보조를 받습니다.
- 불편: 200화가 넘으면서 인물별 비밀과 복선 회수 시점을 엑셀로 관리하고 있습니다.
- 기대: 기존 원고를 가져와 온톨로지를 만들고, 모순과 미회수 떡밥을 미리 경고받습니다.

### P3. IP 기획자 "도윤" (확장 기능 사용자, v1~v2)
- 소규모 콘텐츠 스튜디오 PD.
- 목표: 완성된 화를 씬 단위로 나눠 씬 이미지와 씬 영상을 만들고, 이를 엮어 피칭용 트레일러를 만듭니다.
- 불편: 캐릭터 외형이 컷마다 달라지고 영상 비용을 예측할 수 없습니다.
- 기대: 생성 전에 씬별 프롬프트를 확인·수정·내보내기, 실행 전 비용 견적과 승인 게이트, 캐릭터 시트 기반 일관성, 모델 교체에 흔들리지 않는 프롬프트 자산.

## 4. 핵심 개념과 용어

| 용어 (식별자) | 정의 |
|---|---|
| 작품 (`Novel`) | 최상위 단위입니다. 세계관, 목표, 원고, 예산, 채널 연결, 감사 로그가 모두 작품에 속합니다. Paperclip의 Company(테넌트 루트)에 해당합니다. |
| 목표 (`Goal`) | 작품이 달성할 결과입니다. 장르, 분량, 화수, 결말 방향, 연재 주기, 비축분, 예산을 담습니다. 모든 작업은 목표까지 "왜 하는가" 체인으로 이어집니다. |
| 기획서 (`SeriesBible`) | 시놉시스, 로그라인, 주요 인물, 세계 규칙, 아크 구성을 담은 문서입니다. 사람이 승인하면 그 사실들이 캐논이 됩니다. |
| 아크 (`Arc`) | 여러 화로 이루어진 이야기 단위입니다. 목표, 갈등, 결말 조건을 가집니다. |
| 화 (`Episode`) | 연재 단위입니다. 글자 수 목표, 회차 말 훅, 상태를 가집니다. 상태와 전이는 FR-AGT-12에서 정의합니다. |
| 씬 (`Scene`) | 화 안의 연속된 시공간 단위입니다. 등장 엔티티, 장소, 작중 시점, 원문 위치를 가지며 미디어 확장(샷, 프롬프트, 에셋)의 기준 단위입니다. |
| 샷 (`Shot`) | [확장] 씬을 영상·이미지로 표현하기 위한 카메라 단위입니다. 영상 클립 하나는 4~15초가 현실적 상한이라 씬은 여러 샷으로 나눕니다 [2차]. |
| 씬 영상 (`SceneVideo`) | [확장] 한 씬의 샷 클립을 순서대로 이은 영상입니다. 씬 ID로 역추적됩니다. 트레일러는 씬 영상·클립을 골라 편집한 산출물입니다. |
| 에이전트 역할 (`AgentRole`) | 에이전트의 책임 범위입니다. 4.1절을 참고합니다. |
| 작업 (`Task`) | 에이전트에게 할당되는 업무 항목입니다. 아크·화·씬을 대상으로 하며 상위 목표 링크를 가집니다. 담당자는 하나이고 원자적으로 잠급니다(Paperclip의 Issue와 checkout 패턴). |
| 실행 (`Run`) | 에이전트가 한 번 깨어나 작업을 수행하는 단위입니다. 비용과 로그를 기록합니다. |
| 질문 (`Question`) | 에이전트가 사람에게 묻는 1급 객체입니다. 등급(차단형 `blocking`, 비차단형 `non_blocking`, 정보성 `informational`), 유형, 추천안, 근거, 마감, 상태, 등급 판정 근거를 가집니다. |
| 답변 반영 기록 (`AnswerReflection`) | 답변 하나가 만든 변경(사실·제약·작업 변경), 그 변경을 쓴 후속 실행 ID, 결과물 안의 반영 위치를 묶은 기록입니다(FR-MSG-09). |
| 채널 (`Channel`) | 질문과 알림을 주고받는 외부 메신저 연결입니다(Discord, Telegram 등). 채널 중립 질문 모델을 어댑터가 각 메신저 UI로 바꿉니다. |
| 승인 (`Approval`) | 진행 전 사람의 결정이 필요한 게이트입니다(기획서 확정, 화 승인, 예산 초과, 캐논 변경 등). 승인 요청은 `approve_reject` 유형의 차단형 질문으로 전달되고, 결정 기록(결정자, 시각, 사유)은 승인 객체에 남습니다. |
| 자율성 수준 (`AutonomyLevel`) | 승인 게이트의 위치를 정하는 작품 설정입니다(6.3절의 게이트 표). |
| 질문 민감도 (`QuestionThreshold`) | 비차단형 질문을 얼마나 묻고 얼마나 추천안으로 처리할지 정하는 설정입니다(FR-HIL-06). 자율성 수준과 서로 독립입니다. |
| 세계관 온톨로지 (`WorldOntology`) | 인물, 장소, 조직, 사물, 사건, 규칙, 관계, 인물별 지식을 그래프로 표현한 작품별 지식 저장소입니다. 사실마다 시점, 시간선, 출처, 캐논 상태를 가집니다. |
| 사실 (`Fact`) | 온톨로지의 최소 주장 단위입니다. 예: "A는 3화 시점에 B의 정체를 모른다". 상태는 `candidate`(후보), `approved`(승인), `published_locked`(공개 잠금)입니다. |
| 캐논 (`Canon`) | `approved` 이상 사실의 집합입니다. `candidate`는 캐논이 아닙니다. `approved`를 바꾸려면 승인이 필요하고, `published_locked`를 바꾸려면 명시적 리트콘 승인이 필요합니다. |
| 시간선 (`Timeline`) | 회귀·루프·평행세계를 표현하는 사실의 유효 범위입니다. |
| 떡밥 (`Setup`) / 회수 (`Payoff`) | 복선 설치와 회수입니다. 떡밥은 두 축을 가집니다. 서사 상태는 `planned → planted → reinforced → paid_off` 또는 `abandoned`이고, 캐논 상태는 사실과 같은 `candidate/approved/published_locked`입니다. 회수 기한과 기한 변경 이력, 관련 화·씬·사실을 가집니다. |
| 연속성 이슈 (`ContinuityIssue`) | 생성 원고와 캐논(또는 답변에서 나온 제약, 떡밥 계획)이 충돌하는 후보입니다. 심각도, 근거 사실, 처리 상태를 가집니다. |
| 플랫폼 프로필 (`PlatformProfile`) | 글자 수 기준(공백 포함·제외)을 담은 분량 프리셋입니다. v1부터 최소 회차, 일일 업로드 상한, AI 정책 메모, 확인일을 더합니다. |
| 예산 (`Budget`) / 비용 이벤트 (`CostEvent`) | 작품·기간·기능별 한도와 실제 비용 원장입니다. 소프트 경고와 하드 한도 자동 일시정지가 있습니다. |
| 감사 로그 (`ActivityLog`) | 상태를 바꾸는 모든 동작의 기록입니다. 주체(사람, 에이전트, 시스템), 대상, 이전·이후 값, 근거를 남깁니다. |
| 미디어 대상 화 | [확장] 미디어 흐름을 시작할 수 있는 화입니다. 기본은 "공개 처리된 화"이고 사용자가 바꿀 수 있습니다(FR-SPX-01, 잠정: D-17). |
| 미디어 에셋 (`MediaAsset`) | [확장] 생성된 이미지·영상과 그 출처 기록(모델 ID, 버전, 파라미터, 프롬프트, seed, 레퍼런스, 비용, AI 생성 표시)입니다. |
| 씬 프롬프트 (`ScenePromptIR`) | [확장] 모델 중립 중간 표현입니다. 등장 엔티티, 장소, 소품, 카메라, 분위기, 대사, 시점별 외형, 영상용 모션 정보를 구조화 필드로 담고, 실제 프롬프트는 공급자 어댑터가 렌더링합니다. |
| 렌더링 프롬프트 | [확장] IR을 특정 공급자 문법으로 바꾼 실제 이미지·영상 프롬프트입니다. 생성 전에 보고, 고치고, 내보낼 수 있습니다(FR-SPX-08). |
| 시각 자산 (`VisualReference`) | [확장] 온톨로지 엔티티에 연결된 캐릭터 시트, 승인된 레퍼런스 이미지, 시점별 외형 변화입니다. |
| 공급자 프로필 (`ProviderProfile`) | LLM·이미지·영상 공급자의 모델 목록, 가격, 상업 이용 조건, 콘텐츠 제한, 결과물 보관 기간, 종료 예정일입니다. |

### 4.1 에이전트 역할 (초안)
가정: 역할 구성은 MVP 검증 후 조정합니다. 각 역할은 교체 가능한 LLM 어댑터 위에서 동작합니다.

| 역할 (`AgentRole`) | 책임 | 산출물 |
|---|---|---|

| `planner` | 기획서, 아크 설계, 화별 아웃라인(비트, 훅)을 만듭니다. | `SeriesBible`, 아웃라인 |

| `foreshadow_manager` | 떡밥 설치·강화·회수 계획을 세우고, 원고에 계획대로 들어갔는지 검사하고, 기한을 추적합니다. | 떡밥 리포트, 회수 제안, `paid_off` 제안 |

| `visual_producer` [확장] | 캐릭터 시트, 이미지, 영상 생성 작업을 실행하고 결과를 정리합니다. | `MediaAsset`, 씬 영상 |

## 5. 사용자 시나리오와 여정

### 5.1 작품 생성
1. 민준(P1)이 처음 앱을 설치하면 초기 설정이 LLM API 키 등록, Telegram 연결, 연결 점검을 안내합니다(6.10절).
2. 새 작품을 만들고 장르를 "현대판타지 회귀물"로 적습니다. 장르 템플릿은 v1 기능이므로 MVP에서는 장르와 규칙을 직접 적고, 작품 설정에서 "다중 시간선 사용"을 켭니다(MVP-β).
3. 목표를 입력합니다: 전체 120화, 분량 프로필 "기본(공백 포함 5,000~5,500자)", 하루 1화, 비축분 5화, 결말 방향 "주인공이 회귀 원인을 끊는다", 월 예산 상한, 연령 등급 15세.
4. 자율성 수준을 고릅니다. 기본값은 "화별 승인"입니다.
5. Telegram 연결 화면의 일회용 링크를 열고 `/start`를 누르면 채팅이 작품에 바인딩되고, 확인용 첫 메시지가 옵니다.

### 5.2 기획 확정
1. `planner`가 로그라인 후보 3개를 만들고, `showrunner`가 Telegram 버튼 질문으로 보냅니다(차단형: 작품 방향 결정).
2. 민준이 2번을 고르고 "여주는 회귀 사실을 늦게 알아야 함"을 서술형으로 덧붙입니다.
3. `world_keeper`가 서술형 답을 제약 후보로 바꿉니다: "여주인공은 아크 3 이전에 주인공의 회귀 사실을 모른다(인물 지식 제약)". 해석 확인 질문이 같은 채널로 갑니다. 민준이 "아크 2 끝까지"로 고쳐 답하면 그 내용으로 확정되고, 제약은 `approved` 캐논이 됩니다.
4. `planner`가 기획서(인물, 세계 규칙, 회귀 규칙, 아크 4개)를 만들고 `world_keeper`가 초기 온톨로지를 구축합니다. 확정된 제약이 기획서와 인물 지식에 반영됩니다.
5. 같은 채널로 반영 완료 알림이 옵니다: "답변 반영: 인물 지식 제약 1건, 기획서 아크 2·3 수정. 링크".
6. 민준이 대시보드에서 기획서와 온톨로지 요약을 보고 일부를 고친 뒤 승인합니다. 승인한 사실은 `approved` 캐논이 됩니다.

### 5.3 자율 연재
1. `showrunner`가 1아크를 화 작업으로 나누고 `foreshadow_manager`가 떡밥 배치 계획을 붙입니다.
2. 화마다 아웃라인 → 초고 → 검사(연속성·떡밥) → 검수(문장·분량) → 승인 대기 순서로 진행합니다(FR-AGT-03).
3. 화별 승인 모드에서는 화 승인 질문(요약, 주요 변경점, 연속성 경고 수, 전문 링크)이 옵니다. 민준이 반려하면 사유와 되돌릴 단계를 고르고, 재작성 후 다시 승인 질문이 옵니다(FR-AGT-12).
4. 승인된 화가 비축분에 쌓입니다. 민준이 외부에 올린 뒤 "공개 처리"하면 그 화의 사실이 `published_locked`가 됩니다.
5. 아크별 승인과 완전 자율 모드에서 무엇이 언제 확정되는지는 6.3절 게이트 표를 따릅니다.

### 5.4 메신저 질문 응답
1. 12화 집필 중 `writer`가 "조연 C를 여기서 죽일지"를 결정하지 못합니다. 인물 생사 결정은 기본 차단형 기준(FR-HIL-07)에 해당하므로 `showrunner`가 차단형으로 판정하고 근거를 기록합니다. 추천안, 근거, 마감 시각이 붙습니다.
2. 같은 시간 창의 비차단형 질문 2개(조연 이름, 지명)는 digest 한 통으로 묶여 갑니다. 비차단형은 추천안으로 먼저 진행합니다.
3. 방해금지 시간이 끝난 오전 8시에 메시지가 도착합니다. 민준이 Telegram에서 "살린다"를 고릅니다. 같은 질문이 Discord에도 떠 있었다면 그쪽 메시지는 "답변 완료(Telegram, 08:03)"로 바뀝니다. 이후 Discord에서 다른 답이 오면 늦은 답변으로 처리합니다(FR-MSG-18).
4. 답변은 질문 ID, 영향받는 작업, 온톨로지 노드에 연결됩니다. 12화 작업이 답변 ID를 컨텍스트에 넣고 재개되고, 반영 위치(12화 3번 씬)가 기록됩니다. 다른 화 작업은 그동안 멈추지 않았습니다.
5. 반영 완료 알림이 같은 채널로 옵니다: "C 생존 반영: 12화 씬 3, 사실 2건 추가. 링크".
6. 비차단형 질문에 늦게 답해 추천안과 다른 답이 오면, 해당 화가 공개 전이면 수정 작업이 생기고, 공개 후면 리트콘 승인 질문이 생깁니다(FR-MSG-08).

### 5.5 떡밥 회수
1. 5화에 설치한 "주인공 손목의 흉터" 떡밥의 회수 기한이 40화입니다. 설치 때 `foreshadow_manager`의 떡밥 검사(FR-FOR-08)가 5화 원고에서 설치 씬을 찾아 근거로 연결했습니다.
2. 35화 기획부터 `foreshadow_manager`가 회수 후보 씬을 아웃라인에 제안합니다.
3. **회수 성공**: 38화 초고에 회수가 들어가면 떡밥 검사가 회수 씬과 설치 사실을 대조합니다. 모순이 없으면 `paid_off`를 근거 씬과 함께 제안하고, 38화가 승인될 때 확정됩니다.
4. **회수 누락**: 38화 아웃라인에 배정된 회수가 초고에 없으면 떡밥 검사가 이슈를 만들고, 38화는 승인 대기로 넘어가지 않고 재작성됩니다.
5. **기한 초과**: 40화가 지나도 회수되지 않으면 질문이 자동으로 생깁니다: "기한 연장 / 회수 위치 지정 / 폐기". 민준이 "45화로 연장"을 고르면 기한 변경이 이력에 남고 `foreshadow_manager`가 41~45화 아웃라인을 다시 계획합니다.
6. **모순 회수**: 회수 씬이 설치 때 사실과 어긋나면(예: 흉터 위치가 다름) 심각도 높음 연속성 이슈가 됩니다.

### 5.6 씬 미디어 생성 [확장]
1. 도윤(P3)이 공개 처리된 3화를 미디어 대상으로 고릅니다. `scene_director`가 3화의 모든 씬을 샷으로 나누고 `ScenePromptIR`을 만듭니다. 등장 인물의 해당 시점 외형(의상, 부상)은 온톨로지에서 가져옵니다.
2. 도윤이 미디어 스튜디오에서 씬·샷별 이미지 프롬프트와 영상 프롬프트를 공급자별로 미리 보고, 일부를 고친 뒤 JSON으로 내보냅니다(FR-SPX-08).
3. 주요 인물의 캐릭터 시트를 먼저 생성합니다. 시트 승인 요청이 메신저 `attachment_review` 질문으로 오고, 도윤이 승인합니다. 승인된 시트가 이후 생성의 레퍼런스가 됩니다.
4. 샷마다 저해상도 키프레임 초안을 만들고, 채택한 키프레임만 고해상도로 다시 생성합니다.
5. 3화 전체 씬 영상의 예상 비용이 메신저로 승인 요청됩니다. 승인하면 키프레임을 I2V로 클립으로 만들고, 씬마다 클립을 이어 씬 영상을 만듭니다.
6. 필터에 막힌 샷은 실패 결과로 기록되고, 순화안·이미지 대체·생략 중 무엇을 할지 질문이 옵니다.
7. 결과 화면에서 3화의 모든 씬에 IR, 키프레임, 클립, 씬 영상이 연결된 것을 확인합니다. 원하면 씬 영상을 골라 30초 9:16 트레일러로 편집합니다.
8. 결과물에는 AI 생성 메타데이터와 출처 기록이 붙습니다.

## 6. 기능 요구사항

우선순위: **P0** = 해당 릴리스의 필수, **P1** = 중요(다음 릴리스로 미룰 수 있음), **P2** = 선택. **릴리스** 열은 MVP-α, MVP-β, v1, v2, 이후 중 하나입니다(8절). 범위가 나뉘는 항목은 ID를 a/b로 쪼갰습니다. 확장 영역(6.11~6.14)은 v1/v2입니다.

### 14.2 Paperclip 참고 범위

Paperclip은 AI 에이전트를 하나의 "회사"로 조직해 운영하는 제어 평면입니다. 목표 계층, 작업 할당, 예산, 승인, 감사 로그를 관리하고 에이전트는 어댑터로 깨어나 결과를 보고합니다. 참고 맵: `/private/tmp/claude-501/-Users-snowfall-orca-projects-rea-rea/f618b7ed-232a-40d9-a19b-357147a8e7b1/scratchpad/paperclip-architecture-map.md` (1절 제품 개념, 6절 확장 지점, 8절 재사용 판단표).

**개념 매핑**

| Paperclip | novel-create-studio | 비고 |
|---|---|---|
| Company (테넌트 루트) | `Novel` | 모든 데이터와 예산을 작품 단위로 격리 |
| Goal → Project → Issue 계층, "because" 체인 | `Goal` → `Arc` → `Episode` → `Scene` 계층, 각 계층 대상의 `Task` | 작업은 아크·화·씬을 대상으로 하고 상위 목표 링크를 가짐(FR-AGT-01) |

**재사용 범위 (8절 판단표 요약)**
- **차용 후보(범용 인프라)**: embedded/external PG 런타임과 migration runner, config 로딩, 오류 처리, 주체 모델과 mutation guard, 감사 로그 + 커밋 후 발행 + 실시간 이벤트, storage/secrets registry, plugin host, approvals, documents + revisions, 육각형 모듈 구조와 경계 검사, UI 인프라 골격, CLI 골격(onboard → doctor → run), 설정 보안 모델. PG 런타임은 작업·질문·비용·감사 기록 저장소 후보이며, 세계관 사실·관계·떡밥 연결의 원천은 Graph DB입니다(11절). 코드 차용 전 라이선스 확인이 필요합니다(미확인).
- **패턴만 참고**: 목표 계층, 원자적 checkout, 예산 원장과 정책, wake queue와 run 분리, adapter SPI, MCP facade, 테넌트 스코핑, 인박스·감사 타임라인 UX.
- **미분석(설계 단계에서 확인)**: chat 채널(`@chat-adapter/{discord,telegram}` 패치, chat webhook 라우트, `chat_*` 서비스). 참고 맵은 이를 "교체"로 분류했지만 내부를 분석하지 않았습니다. 요구 2와 직결되므로 Discord·Telegram 어댑터의 재사용 여부를 설계 단계에서 확인합니다(D-15).
- **교체(가져오지 않음)**: agents 조직도·CEO/CTO 메타포·고용 승인, heartbeat 실행 계층과 transcript, 코딩 CLI 어댑터, runner와 sandbox, 클라우드 전용 미들웨어.
- 판단표의 일부 항목(wake queue, adapter SPI)은 Paperclip 쪽 경계를 확인하지 않은 잠정 판단입니다. 설계 문서 단계에서 다시 확인합니다.

- v1 `co_writing` 모드로 본문을 사람이 쓰고 에이전트가 기획·검수·온톨로지만 맡는 사용도 지원합니다. 이 모드가 특정 플랫폼 정책을 충족하는지는 플랫폼마다 판단이 다르며 제품이 보장하지 않습니다.

**저작권**
- **한국**: 문체부·한국저작권위원회 생성형 AI 저작권 안내서(2023-12-27)에 따르면, 인간의 창작적 개입이 없는 AI 산출물은 저작권 등록 대상이 아니고, 등록 시 AI 산출물과 인간 창작 부분을 구분해 적어야 하며 허위 기재는 처벌받을 수 있습니다. AI는 저작자가 될 수 없습니다 [2차]. 2025-06 '생성형 AI 활용 저작물 등록 안내서'는 원문 미확인입니다.
- **미국**: 저작권청 보고서 Part 2(2025-01-29)는 프롬프트만으로는 보호받지 못하고, 사람의 표현적 입력이 지각 가능하게 남은 부분과 사람의 선택·배열·수정은 보호될 여지가 있다고 봤습니다. 대법원은 2026-03-02 Thaler v. Perlmutter(No. 25-449) 상고를 기각해 D.C. Circuit 판결과 인간 저작자 요건이 유지됐습니다 [2차, SCOTUSblog 사건 페이지 포함].

**AI 생성 고지와 표시**
- **한국 AI기본법(2026-01-22 시행)**: 생성물 표시 의무는 AI 사업자에게 있고, 딥페이크성 생성물은 명확히 표시해야 하며, 서비스 밖으로 내보낼 때는 워터마크가 필요하고 기계 판독형 비가시 워터마크도 허용된다는 해설이 있습니다. 이용자에게는 의무가 없다는 해설과 "개인 웹툰 연재는 무방"이라는 보도가 있습니다. 과태료는 최대 3천만 원이라는 보도가 있고, 시행령 입법예고에 과태료 적용 전 최소 1년 계도기간이 들어갔다는 보도가 있습니다. 시행령 최종 조문은 확인하지 못했습니다 [2차].
- **제품 영향**: 제품을 서비스로 제공하면 우리가 의무 주체가 될 수 있습니다(가정: 로컬 자체 호스팅만 제공해도 해당하는지는 법률 검토 필요, D-12). Veo 결과물에는 SynthID가 자동 삽입된다는 보도가 있습니다 [2차].

**미디어 모델 이용약관과 콘텐츠 제한**
- **인물 생성 제한(종료된 모델 기준 사례)**: Veo 3.1 Preview(2026-10-22 종료)는 I2V, 보간, 레퍼런스 모드에서 `allow_adult`만 허용해 레퍼런스 기반 미성년 인물 생성이 안 됐고, EU·UK·스위스·MENA에서는 모든 모드가 `allow_adult`로 제한됐습니다 [1차, 종료 전 확인]. 후속 공급자도 비슷한 제한을 둘 수 있으므로 학원물·아동 캐릭터 영상화가 막힐 수 있다고 가정합니다. 후속 모델의 실제 제한은 [미확인]입니다(D-19).
- **실존 인물**: 주요 공급자 정책은 실존 인물 사칭과 동의 없는 합성을 금지합니다(정책 원문은 이번 조사에서 다시 확인하지 않음). Seedance 2.0은 실사 얼굴 레퍼런스를 차단한다고 합니다 [2차].
- **선정성·폭력**: 상용 API는 노골적 성적 콘텐츠를 일반적으로 금지하고 과도한 폭력을 필터링합니다. 안전·기억 필터로 결과가 차단될 수 있습니다 [1차, 종료된 Veo 기준].
- **상업 이용**: FLUX.2 [dev] 가중치는 비상업 라이선스이고 출력물의 상업 이용 해석은 출처마다 다릅니다. LTX(OpenRAIL), HunyuanVideo(EULA)는 라이선스 제약 확인이 필요합니다. Wan 2.2는 Apache 2.0입니다 [2차, 미검증].
- **학습 데이터 분쟁**: MPA와 할리우드 스튜디오가 Seedance에 저작권 침해 경고장을 보냈다는 보도가 있습니다 [2차]. 공급자 선정 시 검토 항목으로 둡니다.
